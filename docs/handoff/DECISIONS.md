## D-001 · 2026-10-24 · 프로젝트를 빈 폴더에서 새로 시작
- 결정: 이 폴더(`Hello_Archive jr`)를 프로젝트 루트로 삼아 Next.js를 새로 생성한다.
- 배경: SESSION 00 시작 시 폴더에는 학습용 HTML/CSS/JS, `PROJECT_CONTEXT.md`, `AGENTS.md`, 그리고 Next.js 16.4.2 기반 `mvp/`(단일 클라이언트 컴포넌트, 순수 CSS, 일회용 코드 인증, 체험 모드, 태어난 달만 저장)가 있었다. 분석 중 사용자가 "다 지웠어 처음부터 새로 생성해"라고 지시했고, 폴더가 비어 있음을 확인한 뒤 새로 시작했다.
- 선택 이유: 지침의 스택(Tailwind, App Router 라우트 구조, 세션 순서)에 맞춰 깨끗하게 시작.
- 고려한 대안: 기존 `mvp/` 확장 (사용자가 삭제하여 불가).
- 영향: 이전 `mvp/`의 구현(한국 시간 주차 계산, RLS 스키마 아이디어)은 코드로 남아 있지 않다. 필요한 로직은 해당 세션에서 다시 작성하고 테스트한다. 이전 `PROJECT_CONTEXT.md`의 Meta 광고·인터뷰 계획 등 맥락은 사라졌으므로 `PROJECT_BRIEF.md`에는 확인된 요약만 담았다.

## D-002 · 2026-10-24 · Next.js 16.4.3 + 스캐폴드 기본 설정 유지
- 결정: `create-next-app@16.4.3` (TypeScript, Tailwind v4, ESLint, App Router, `src/`, Turbopack, npm, React Compiler 미사용). 의존성은 `package-lock.json`으로 고정.
- 스캐폴드 기본값으로 `next.config.ts`에 `cacheComponents: true`, `partialPrefetching: true`가 켜져 있다. 임의로 끄지 않았다.
- 영향: Cache Components에서는 쿠키·세션처럼 요청 시점 데이터를 읽는 컴포넌트에 `<Suspense>` 경계가 필요할 수 있다. **SESSION 03(인증)에서 공식 문서(`node_modules/next/dist/docs`)로 호환성을 확인**하고, 방해가 되면 이 설정을 끄는 결정을 새 항목으로 남긴다.
- `middleware`는 이 버전에서 `proxy.ts`로 이름이 바뀌었다. 보호 라우트는 `src/proxy.ts`로 구현한다 (SESSION 03). proxy는 낙관적 차단용이고 최종 권한 검증은 서버 코드·RLS에서 한다.

- 이 Next.js 버전의 `error.tsx`는 `reset`이 아니라 `retry` prop을 받는다.
- 라우트 그룹 `(public)`/`(app)` 도입 (ARCHITECTURE.md의 설계대로). 로그인·콜백·온보딩 라우트는 만들지 않았다.

## D-011 · 2026-10-24 · 화면 전환 애니메이션: React `<ViewTransition>` (라이브러리 추가 없음)
- 계기: 사용자 요청("내비게이션 이동 시 스무스한 무빙").
- 결정: React 19.3 `<ViewTransition>` + Next `<Link transitionTypes>` 사용 (`node_modules/next/dist/docs/01-app/02-guides/view-transitions.md`). ① `src/app/(app)/template.tsx`가 페이지를 감싸 방향 슬라이드(`nav-forward`/`nav-back`, 350ms) ② 메뉴 빨간 밑줄은 `name="nav-indicator"`로 선택한 메뉴로 미끄러져 이동 ③ 방향: 메뉴 순서(홈→기록 쓰기→아카이브→프로필)상 오른쪽이면 forward, 왼쪽이면 back. 목록→상세·기간 묶음은 forward, "← 아카이브"는 back ④ `prefers-reduced-motion`이면 애니메이션 끔. CSS는 `globals.css` 하단.
- 레이아웃이 아닌 `template.tsx`를 쓴 이유: 레이아웃은 이동 시 유지되어 enter/exit가 실행되지 않는다. 템플릿은 이동마다 새로 만들어진다 (동작 확인함).
- 타입: ViewTransition 타입은 `react/experimental` 선언에 있어 `src/types/react-experimental.d.ts`로 참조.
- 한계: 브라우저 View Transitions 지원이 필요하다(미지원이면 애니메이션 없이 정상 이동). 브라우저 뒤로가기 버튼은 방향 타입이 없어 슬라이드되지 않는다. 홈 허브의 탭 전환·펼침은 라우트 이동이 아니라 이 효과 대상이 아니다.

## D-013 · 2026-10-24 · SESSION 02 DB 구현 방식 (D-005 확정)
- 환경: **개발용 원격 Supabase 프로젝트** + SQL Editor 수동 적용. 이 PC에는 Supabase CLI·Docker가 없다. 실서비스(베타) 프로젝트와 분리한다.

- `src/types/database.ts`는 CLI 없이 **손으로 작성**했다. 마이그레이션과 어긋나지 않게 같이 고친다.
- 목 데이터 교체 시점: DB 조회는 로그인(RLS의 `auth.uid()`)이 있어야 가능하므로 `mock-data.ts` 교체는 SESSION 03(인증) 이후 04~05에서 한다. SESSION 02에서는 화면을 바꾸지 않았다.

## D-014 · 2026-10-24 · 빈 텍스트 검사는 정규식으로 (btrim 사용 금지)
- 계기: RLS 테스트에서 `"   \n "` 본문이 `char_length(btrim(body)) >= 1` 검사를 통과했다. `btrim`은 기본적으로 스페이스만 제거해 줄바꿈·탭만 있는 값이 비어 있지 않은 것으로 판정된다.

## D-015 · 2026-10-24 · 장기 방향: 웹 MVP → 설치형 웹(PWA) → 네이티브 앱 (사용자 계획)

## D-016 · 2026-10-24 · 인증은 이메일 일회용 코드(OTP) 입력 방식 (D-006 확정)

## D-017 · 2026-10-24 · 커스텀 SMTP(Resend) 필요 — 메일 템플릿 수정 조건

## D-019 · 2026-10-24 · 자녀 프로필: 온보딩·수정 방식과 입력 규칙 (D-005, D-013 후속)

- 오류가 나도 입력값을 돌려줘 폼이 비워지지 않는다. 오류 로그에는 오류 코드만 남기고 별명·생년월일은 남기지 않는다.

## D-021 · 2026-10-25 · 아카이브 기간 묶음: 달력 고정 구간, 작성일(KST) 기준 (D-007·D-009 임시 기준 폐기)

## D-039 · 2026-10-28 · 홈과 저장된 기록의 질문 불일치: 완료된 기록은 자기 질문으로, 한 주의 기록은 하나

- **원인(코드·시드 대조로 확인)**: D-038로 같은 주에 시기별 질문 행이 여럿(`weekly_questions (week_start, stage)`)이 됐다. 기록(`entries`)은 쓸 당시의 질문 행 하나에 매달리고, "질문 바꾸기"(`week_question_choices`)도 질문 행마다 따로 저장된다. 홈은 완료 카드에도 "지금 아이 시기의 질문 행 + 그 행의 선택"을 그렸고, 최근 기록·상세·카드는 기록이 매달린 행의 질문을 그렸다. 두 행의 선택이 달라(두 문구 모두 질문 은행에 있는 문구) 어긋났다. 같은 원인이 두 가지 데이터 위험도 만들었다: (a) 홈에서 "수정 저장"하면 질문 id로 기존 기록을 찾아 못 찾고 **같은 주에 두 번째 기록을 새로 만들 수 있었다**, (b) 놓친 질문 목록이 다른 시기 행에 기록한 주를 "놓친 주"로 셀 수 있었다.
- **결정**: ① 이번 주 카드의 질문 = 기록이 있으면 **저장된 기록의 질문**, 없으면 지금 시기의 추천 질문(`questionForWeekCard`). 추천 질문은 기록이 있으면 화면에 보내지도 않는다. ② "같은 주"는 질문 id가 아니라 **`week_start`**로 판단한다: 기록 찾기·저장(`findWeekEntry`, `saveEntryForQuestion`), 놓친 질문(`answeredWeekStarts`), 질문 바꾸기 대상 행(기록이 있으면 그 기록의 행). 기존 기록은 자기 질문 행에 그대로 두고 본문만 고친다. ③ 기록 완료 상태에서는 질문 바꾸기 도구(새로고침 아이콘·직접 질문 쓰기·되돌리기)를 기본 화면에서 감추고, **수정 흐름 안의 "질문도 바꾸기"**를 눌러야 열린다(바꾸면 이 기록에 보이는 질문도 바뀐다는 경고 포함). 취소하면 저장된 원본이 그대로 남는다.
- **하지 않은 것**: 기존 기록의 질문을 추측해서 채우거나 덮어쓰지 않았다(DB 변경 없음). 기록에 질문 문구를 복사해 두는 "스냅샷 컬럼"은 두지 않았다 — 질문 문구는 여전히 `기록 → 질문 행 + 그 행의 선택`으로 읽는다. 질문 행의 `body`를 운영자가 시드로 바꾸면 기존 기록의 질문도 바뀐다(D-038의 "기록 있는 주의 문구는 시드가 바꾸지 않음"이 그 보호). 완전한 스냅샷이 필요하면 `entries.question_body`(nullable, 기존 기록은 비워 둠) 추가가 후속 후보다.
- 검증: 단위(`week-question.test.ts`, `missedQuestions`), DB(`test:entries` 시기별 질문 행 3개 추가), 개발 DB에 실제 상황 재현(만 10세, 기록은 `early` 행 + 두 행에 서로 다른 선택) 후 홈·`/write`·아카이브·상세·월/분기/연 챕터·카드의 질문 일치 확인, 홈 "수정 저장"이 새 기록을 만들지 않음, 수정 흐름에서 질문 바꾸기가 기록의 행에 적용됨(추천 행의 선택은 그대로).

## D-045 · 2026-10-28 · 개발 중 `instant` 검증 콘솔 오류 끄기
- 현상: 개발 서버에서 소개의 "이메일로 시작하기"를 누르면(로그인 상태면 `/login`→`/home`) 개발 오버레이에 `Route "/home": Could not validate instant ...`가 뜬다. 원인: Cache Components의 개발용 "즉시 이동 검증"(기본 `validationLevel: 'warning'`)이 모든 페이지를 로그인 정보 없이 미리 그려 보는데, 로그인이 필요한 화면은 `requireUser()`가 `/login`으로 이동(NEXT_REDIRECT)해 항상 실패한다. 서버 로그의 cause가 `src/lib/auth.ts`의 `redirect("/login")`이다.
- 결정: `next.config.ts`에 `experimental.instantInsights.validationLevel: "manual-warning"`(`instant`를 직접 내보낸 화면만 검증). 개발 중 경고일 뿐 실제 동작·프로덕션에는 영향이 없다. 근본 해결(세션 읽기를 `use cache: private` 등으로 정리해 이동을 즉시로 만들기)은 별도 과제다. 이 경고가 이번 변경 이전에도 났는지는 확인하지 않았다.
