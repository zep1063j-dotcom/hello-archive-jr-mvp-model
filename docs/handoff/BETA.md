# BETA — 약 5명 부모 베타 운영안 (SESSION 09)

> 상태: **초안**. 성공 기준(2절)은 사용자 확정이 필요하다(문의 창구는 확정됨). 확정 전에는 가설이며, 5명의 결과로 시장 수요를 입증했다고 말하지 않는다.

## 1. 무엇을 검증하나
- 가설 H1: 바쁜 부모도 매주 질문 1개에 텍스트로 답해 기록한다 (관심이 아니라 **행동**).
- 가설 H2: 기록이 쌓인 결과물(월/분기/연 챕터)에 가치를 느낀다. 지불 의향은 이번 베타의 측정 대상이 아니다(인터뷰에서 신호만 듣는다).
- 방법: 4주(질문 4개) 사용 + 2번의 짧은 대화(2주 차, 4주 차).

## 2. 성공 기준 (초안 — 사용자 확정 필요)
측정은 `supabase/analytics/beta_metrics.sql`(운영자 본인·시험 계정 제외). 분모는 **자녀 등록까지 마친 부모**.
5명·4주 최소 운영 집계(D-043): 첫 기록 완료 인원 = 쿼리 4 `wrote_once`, 주차별 기록 인원 = 쿼리 1 `writers`, **4주차 기록 인원 = 쿼리 5 `week_no=4`의 `writers / eligible_parents`**, 기록 횟수 = 쿼리 4 `total_entries` / 쿼리 5 `entries`. 자발적 재방문·운영자 독촉 여부·미작성 이유·카드 만족도는 5절의 대화 메모(운영표)로 보완한다. 아래 4가지 외의 측정(로그인 이후 방문·클릭·메일 열람 등)은 처리방침 변경이 필요하다.

| 지표 | 정의 | 기준(초안) | 이유 |
|---|---|---|---|
| 활성화 | 초대 → 자녀 등록 완료 | 5명 중 4명 이상 | 로그인 코드 한 단계가 장벽인지 본다 |
| 첫 기록 | 자녀 등록 후 7일 안에 첫 기록 (`hours_to_first` ≤ 168) | 5명 중 3명 이상 | 첫 주에 못 쓰면 대부분 돌아오지 않는다는 가설 |
| **지속(핵심)** | 4주 중 3주 이상 기록한 부모 (`weeks_written` ≥ 3) | 5명 중 3명 이상 | H1의 직접 증거 |
| 이탈 신호 | `weeks_since_last` ≥ 2 | 기준 없음, 발생 시 당사자에게 이유 묻기 | 숫자보다 이유가 중요 |
| 메일 기여 | 메일 발송 후 24시간 안에 쓴 비율 (쿼리 2) | 기준 없음, 관찰만 | 월요일 19시가 맞는지 가설 확인용 |
| 글 길이 | 기록 평균 글자 수 | 기준 없음 | 너무 짧으면 질문·입력창 부담 의심 |

판단 규칙(초안):
- 지속 3/5 이상 → H1 잠정 지지. 다음 베타(더 넓은 모집)와 챕터 가치 인터뷰로 진행.
- 지속 1~2/5 → 이탈한 부모에게 이유를 듣고(질문 난이도 / 메일 시각 / 쓰기 부담 / 기록할 일이 없음) **한 가지 변수만** 바꿔 2~4주 재시도.
- 지속 0/5 → 기능 추가 금지. 인터뷰로 "왜 안 썼나"를 먼저 확인.
- 한계: 5명은 통계가 아니다. 비율 대신 n/N으로 읽고, 초대받은 지인이라 **호의 편향**이 있다(실제 시장보다 높게 나올 가능성).

## 3. 측정 방법과 개인정보
- 앱 **안**(로그인 이후)에는 분석 도구·이벤트 전송을 **넣지 않는다**. 로그인 전 공개 화면(소개·로그인·약관)에만 GA4 방문 측정을 둔다(D-035). 이미 DB에 있는 행(`entries.created_at`, `email_deliveries`, `children.created_at`)만으로 계산한다. 그래서 본문·자녀 정보가 외부로 나가지 않는다 (CLAUDE.md 원칙).
- 쿼리는 본문·이메일·자녀 이름을 조회하지 않는다. 부모는 "부모 1, 2…"로만 보인다. 정식 Supabase SQL Editor에서 쿼리를 **하나씩** 실행한다(여러 문장을 한꺼번에 돌리면 마지막 결과만 보인다). service role 키를 이 Mac에 둘 필요가 없다.
- 제외 계정: 쿼리 맨 위 `excluded` 배열에 운영자 본인·시험 계정의 user_id를 넣는다(Authentication > Users에서 복사).
- 한계: 앱을 열었는지(방문)·메일을 열었는지는 모른다. 측정하는 것은 "기록했는가"뿐이다. 메일 열람 추적(픽셀)은 개인정보 원칙상 넣지 않았다.
- 매주 월요일(발송 직전) 쿼리 1·3을 확인하고 한 줄 메모를 남긴다(예: 이탈 징후 부모, 메일 failed 수).

## 7. 삭제 요청 대응 (수동 절차, 앱 기능은 미구현)
부모가 문의 창구로 삭제를 요청하면 운영자는 **먼저** 정식 Supabase 대시보드 > Storage > `photos` 버킷에서 그 사용자 id 이름의 폴더(사진 파일)를 지운 뒤(DB 삭제는 파일을 지우지 않는다, D-027), Authentication > Users에서 해당 사용자를 삭제한다. `auth.users` 삭제가 `parent_settings`·`children`·`entries`·`email_deliveries`로 cascade된다(DB 테스트로 확인됨, `test:rls`). 삭제 후 `entries`·`children` 행이 0인지 SQL Editor로 확인하고, 요청자에게 완료를 알린다. Resend 쪽 발송 이력(수신자 주소)은 별도 보관되므로, 처리방침에서 보관 기간을 정해야 한다(미정, 법률 검토 필요).

### 7-1. 기록 내보내기 (앱 기능 없음, 운영자 수동 제공 — 사용자 확인 필요)
앱에는 전체 기록 내보내기 기능이 없다. 부모가 "내 기록을 받고 싶다"고 문의하면 운영자가 **본인 확인 후** 정식 Supabase 대시보드 SQL Editor에서 그 부모의 `entries`(본문·작성일·질문)를 조회해 파일로 보내고, 사진은 Storage `photos` 버킷의 그 사용자 폴더에서 내려받아 전달한다. 앱 화면과 처리방침은 이 절차를 약속하지 않고 "삭제 요청 이메일"만 안내한다(처리방침 7항의 "보고 고치고 삭제"는 앱 화면 + 삭제 요청으로 가능한 범위). 이 절차를 실제로 해 본 적은 없다.
